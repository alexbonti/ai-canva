2.1 Route A — set up the team boards (facilitator path)

You need an account that is admin or facilitator (grant it from the Admin board, or POST /api/admin/roles). Once granted, the header shows the 🧑‍🏫 Facilitator button.

  1. Create one template board per track. Header → Facilitator → Templates tab → create a template board per track (e.g. "Cyber — Sprint tasks"). Templates stay out of the normal board list.
  2. Add the task list to the template. Open the template board → + Add Box → Collaboration → Checklist. In the box's Add a task… field, paste that track's block from §5 — a multi-line paste becomes one task per line.
  3. Create the workshop. Facilitator → Workshops tab → new workshop for the class.
  4. Create one team per student team. Facilitator → Teams tab → create the team from the track's template. Each team gets its own copy of the board (so Team A's ticks never touch Team B's) plus a per-seat join code.
  5. Hand each team its join code (one code per seat, up to 5 seats).
  6. Students join: landing page → 🎟️ Have a workshop code? → paste the code → pick a name (and an email — see the caveat below) → Join my team → their team board opens with the checklist already on it.
  7. Run it from the board each day: students tick tasks off, rename a task by clicking its text, pick an owner in the ＋ assign dropdown, reorder with ▲▼, and 📋 Copy exports the list as a Markdown checklist (that export is exactly the "evidence of collaboration / task tracking" the group briefs' teamwork mark asks for). 🧹 Clear done at a sprint boundary for a clean board.
Local vs deployed: granting the facilitator role (POST /api/admin/roles) needs the Firebase Admin SDK, so it returns 501 on the local dev server — do it from the deployed site (or the Firebase console). Guest joining does work on localhost: the dev server proxies /api/workshop/join to the deployed function, so you can rehearse the whole flow locally.

2.2 What the app does and doesn't do (verified against the code)

  • The list is shared and live — one list per Checklist box, everyone on the board sees the same tasks; writes are last-write-wins, like a Note.
  • A tick records who ticked it and when (✓ alice next to the task), and a progress bar shows "2 of 5 done" — enough to grade the task-tracking part of the teamwork mark.
  • Caps: max 200 tasks per board, 500 characters per task — keep a sprint's list to ~20–25 tasks and clear finished ones between sprints.
  • Guest caveat (matters for workshop students): the ＋ assign dropdown and the ✓ name attribution are email-based (board owner + collaborators + people currently on the board). A student who joins with a seat code has no auth email, so their tick shows no name, and they only appear as an assignable person if they typed an email at the profile step (that email is stored on the board's collaborator list; it is never used to log them in). Students who sign in with a Google account have none of these limits. Making seat-code guests properly assignable and credited needs a small code change (use the guest's uid + chosen name for checklist identity).
  • The Checklist box is a collaboration box: no AI, no Run button, no connectors. It is a to-do list that lives on the board.

5. Paste-ready Checklist blocks

Paste a whole block into a Checklist box's Add a task… field — a multi-line paste imports one task per line. Each line carries its ID, owner and due week, and students can rename, assign and tick them in place. For group tracks use that track's Sprint 1 block, then paste the Sprint 2 block at the Week 3 boundary and the Sprint 3 block at Week 6.

7. Notes that keep this honest

  • Tasks map to the briefs' own criteria — no hidden extra marks. If you change a rubric, change the matching task row here too.
  • The board is the artefact. A team that finishes the tool but leaves an empty checklist has no task-tracking evidence for the 20% teamwork mark.
  • Caps: 200 tasks per Checklist box, 500 characters per task — clear done tasks between sprints.
  • Guests: seat-code students should type an email at the profile step, otherwise they can't be assigned tasks and their ticks are anonymous (see §2.2).
