AI-Assisted Software Project · Group Capstone

Cybersecurity & Compliance Support Tool

Repurpose AI Canva into a tool that helps people design security policies & use cases, and check them against real standards.
Mode: Group
Team: 4–5 (UX · BA · Dev · Cyber)
Build: 40%
Research: 40%
Teamwork & Demo: 20%

1. Overview

Your team will turn AI Canva — a visual pipeline tool where users place "boxes" on a canvas and AI content flows box-to-box — into a cybersecurity & compliance support tool.

The tool helps people who need to:

  • Design security policies and cybersecurity use cases / project proposals, and
  • Check / vet those use cases and proposals against real standards and frameworks.

It provides three kinds of boxes:

  1. Design boxes — help author a use case (asset inventory, threat model, policy draft, security requirements).
  2. Check boxes — audit/vet a use case against frameworks (NIST, ISO 27001, OWASP, GDPR, risk scoring, gap analysis).
  3. An assistant — a tailored AI assistant that guides users through designing and checking.
Example use case: a team is "moving customer data to a new cloud vendor." The tool helps them: map the assets → model the threats → draft a policy → check it against NIST/GDPR → score the risk — and an assistant guides them through each step.

4. How the boxes fit together (the demo pipeline)

The three roles form a loop: design → check → guide.

💡 Idea (raw proposal)
   └─▶ 🛡️ Asset Mapper (design) ──▶ 🧠 Threat Modeler (design) ──▶ 📜 Policy Drafter (design)
                                                                     └─▶ ✅ NIST Checker (check)
                                                                     └─▶ 🎯 Risk Scorer (check)
   └─▶ 🤝 Security Advisor (assistant)  ← guides the user at any step

Each box plugs into AI Canva through the shared scaffold (3 touchpoints): types.ts (register), boardStore.ts (runBox branch), BoxNode.tsx (optional custom render). Because every box speaks the same {{inputs}} language, any box plugs into any pipeline.

5. Deliverables

A. Working tool (Build — 40%)

  • At least 3 boxes (one per role) wired into the scaffold
  • A working demo pipeline (design → check → assistant)
  • Clean, readable, commented code; runs locally (npm run dev)

B. Research & design report (40%) — 3,000–4,000 words:

  1. Problem & motivation
  2. Domain research (the frameworks you used)
  3. Design rationale (boxes, prompts, outputs)
  4. Alternatives (manual, GRC tools, consultants)
  5. Ethics & limits (false assurance, legal weight, hallucinated controls) + guardrails
  6. Team reflection (how each skill contributed)

C. Demo & teamwork (20%) — live demo on a real use case + evidence of collaboration (PRs, reviews, task tracking).

6. Sprints & timeline

The project runs over 3 sprints, 8 weeks total. Each student can work 10 hours per week (80 hours total per student; a team of 4–5 has ~320–400 team-hours).

SprintDurationHours/studentFocus
Sprint 12 weeks (starting today)20 hrsResearch, team roles, box selection, scaffold
Sprint 23 weeks30 hrsMain build — implement the boxes
Sprint 33 weeks30 hrsFinish build, research report, demo

Sprint 1 — Research & scaffold (2 weeks, 20 hrs)

  • Lock team roles (UX / BA / Dev / Cyber)
  • Choose your 3+ boxes (one per role) and the demo pipeline
  • Research question + 3 sources per member
  • Register boxes in types.ts + draft prompts

Exit: a clear plan and a scaffolded repo.

Sprint 2 — Main build (3 weeks, 30 hrs)

  • Implement runBox branches for all chosen boxes
  • Wire the AI backend; boxes produce real output
  • Build the demo pipeline (design → check → assistant)
  • Mid-sprint check: at least one box fully working end-to-end

Exit: a working tool with all boxes chaining.

Sprint 3 — Finish, report & demo (3 weeks, 30 hrs)

  • Polish: error handling, custom rendering, edge cases
  • Write the research & design report (3,000–4,000 words)
  • Prepare the live demo on a real use case
  • Collect teamwork evidence (PRs, reviews, task tracking)

Exit: a finished tool, report, and demo.

Sprint rule: at the end of each sprint, demo what you have — even if it's rough. A working partial tool each sprint beats a broken "complete" one at the end.

8. Guidelines

  • Use AI to build — but be able to explain every box.
  • Cybersecurity accuracy matters — the cyber member(s) must verify the tool's security/compliance advice is technically sound. A wrong NIST control ID or a misjudged GDPR obligation is a real error.
  • Be honest about limits — acknowledge where AI security advice is not trustworthy (can't truly verify code, can hallucinate control IDs, not legal advice).
  • Every skill contributes to research AND build — no one is "just the coder" or "just the designer."
Good luck. You're building a tool that could genuinely help people make better security decisions. The combination of your skills — UX, analysis, development, and cybersecurity — is exactly what a real security product team looks like. Design it well, build it soundly, and justify every choice.
